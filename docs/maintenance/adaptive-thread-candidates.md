# Adaptive thread delivery candidates

For MESSAGE_CREATE on a loaded, unarchived forum thread, candidate selection compares the existing exact ETS membership counter with the number of unique users in the guild's online-session index. Ties use the membership direction. The membership direction retains member_ids followed by for_users; the online direction probes current ETS membership once per unique online user and expands every matching device. SID maps deduplicate candidates before mentions and watch sessions are merged.

The counter is read in O(1). Existing insert/remove operations maintain it idempotently, and handoff import rebuilds it from membership rows. No member list is constructed to choose a direction. The online index keeps its existing session-map reference invalidation. No membership or permission result is cached across messages.

Unknown counters, archived or absent threads, missing metadata, other events and non-forum parents retain the original path. Missing storage retains its original error or snapshot behavior. Final interest, viewer, pending, permission, passive and watch-lease checks are unchanged. Direction is a count heuristic; an ETS membership probe and a map lookup have different costs, so this does not imply a particular CPU improvement.

The supplied handoff fixture `guild_adaptive_candidates_tests.erl` checks both directions, 100000 memberships, 4000 online users, small/equal/empty/offline sets, devices, membership changes and import. It is run from an isolated validation directory, not added to the product test tree. With `ADAPTIVE_ORACLE` and test-only `export_all`, it also compares exact candidate maps and final SID/session pairs against the pre-integration dev gate, including a 100000-member, 4000-online, 2000-watch fixture. Small fixtures exercise revoked permission, mentions, watch expiry, pending/viewer/passive state, archive/restore, unknown count and missing-store behavior. The integration validation increases only the isolated oracle harness timeout from 30 to 180 seconds; it does not change a product RPC budget or run a capacity load test. See the delivery package validation report for commands and results.
