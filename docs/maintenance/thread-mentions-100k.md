# Mentions-only thread notifications and 100,000 followers

Thread messages use device push only for explicit direct/reply mentions and admitted role candidates. Everyone/here keep display and WebSocket behavior but never cause thread device push or automatic joins. Ordinary channels, DMs, calls and notification clearing keep their existing contracts. A role with 3,001 holders is excluded; after excluding large roles, a distinct role union reaching 3,001 excludes all roles. Unknown indexes skip roles, independently of direct mentions. The existing stable ordering, available room and at-most-250 role supplementation happen before permission/policy filtering, without backfilling skipped candidates. Final subscription checks remain; no device eligibility cache is included.

A private immutable per-message decision is stored in `thread_message_mention_decisions`. Retry workers reuse that decision and recheck current permissions. Public warnings contain only reason codes, never counts, IDs or the decision. Message/thread deletion removes private decisions.

## Frozen outsider admissions (protocol v2)

The private decision is now **version 2** and contains required `role_add_user_ids`: at most 250 unique original nonmembers, a subset of `role_user_ids`, excluding the author and direct-mention recipients. This immutable allowlist is persisted inside the existing `decision_text` JSON; it needs **no new database column or bulk backfill**. Insert and load validate it. Workers may recheck and shrink eligibility, but never replace failed candidates or admit an original member who later left merely because that ID remains in the role notification set. Retries reuse the original allowlist rather than resetting an outsider-selection budget.

Legacy version-1 records remain readable with an absent/empty admission list. The existing bounded frozen `role_user_ids` remain device-push notification candidates under current-role, channel-view and device checks, even if a candidate is no longer a thread member; this never authorizes an inferred join. Worker processing retains current-member and direct/reply behavior; **only new role autojoins fail closed**. Never infer or backfill a missing allowlist from current roles/membership, and never strip version-2 fields to make an old worker accept a record.

## Compatible schema and deployment

The migration entry is `thread-mentions-100k.cql`; the canonical schema is `tools/dev/cassandra_target_schema.json`. Inspect actual Cassandra columns before executing each missing-column ALTER. Add `deleting boolean`, `delete_ticket text`, `delete_prepared_state_version int`, and `delete_dispatched boolean`, plus the decision table. Existing null booleans are false. Postgres KV stores these fields in its existing generic row representation; no dedicated SQL table is added. The final channel/state cleanup uses the existing atomic batch API (Cassandra logged batch / Postgres transaction); a Cassandra logged batch is not a cross-partition read-isolation guarantee.

Do not drop or redefine old `delete_prepared_version bigint`. If it exists, audit every row using paging, preserve original ticket and version, and use the documented conditional backfill template only for exact int-range values into a null new field. Every LWT must be applied or reread. Nonempty conflicting fields, missing tickets, oversized versions, or partially purged old-candidate records need explicit recovery before enabling this deployment. An old keeper cannot be recreated from an already truncated audience. Do not set `delete_dispatched` true without verified owner processing. Old reader/writer artifacts continue to use the retained old column until migration and drain finish.

Deploy compatible schema first. Before upgrading, pause affected thread-message acceptance and stop/drain **all old `handleMentions` consumers**: an old worker processing an old queued record still has its historical retry behavior, which a new capability lease cannot change retroactively. Deploy all Gateway owner/router, API and worker instances with the v2 contract. Capability response, API/worker registration, resolve-request version fields and dedicated thread-dispatch protocol are all **2**; version-1 leases do not satisfy readiness and old workers reject version-2 decisions. Mixed-version thread dispatch is deliberately unavailable rather than falling back to the old owner/broadcast path. Each API/worker uses a stable per-replica `FLUXER_THREAD_MENTION_INSTANCE_ID`. Gateway activation uses `FLUXER_GATEWAY_THREAD_MENTIONS_ENABLED` and exact comma-separated rosters `FLUXER_GATEWAY_THREAD_MENTIONS_EXPECTED_API_INSTANCE_IDS` / `FLUXER_GATEWAY_THREAD_MENTIONS_EXPECTED_WORKER_INSTANCE_IDS`; configured expected counts must match unique roster sizes. IDs use ASCII letters, digits, dot, underscore, colon or hyphen, 1–128 characters. Corresponding JSON settings are under `services.gateway.thread_mentions`. Defaults are disabled. After old API/worker instances are drained, wait at least a full 60-second lease lifetime before activation. Verify that every active Gateway and every exact configured API/worker identity is v2-ready, then resume acceptance/queues and deploy client warnings/settings. An instance count alone is not evidence of this contract. Incomplete capability checks use the bounded direct-only path; an old Gateway rejects the dedicated new thread RPC rather than receiving a legacy broadcast payload. Failed direct delivery is an error, not permission to broadcast.

The 100,000 admission cap is implemented in the product constants, not switched by the mentions flag. Therefore keep joining traffic drained until all loaders and lifecycle paths are compatible. Existing-member joins remain idempotent at capacity. Cold loads use 1,000-row pages and bounded per-thread enumeration, with failures rather than partial publication.

## Deletion and restart recovery

Preparation reads a version/count-checked audience outside the guild owner, then a CAS freezes membership and persists its ticket/prepared version. The original API RPC transport remains 5 seconds; snapshot loading has a 4-second deadline, per-page calls at most 2 seconds, reserve/installation calls 250/500 ms. Timeouts propagate as errors and do not authorize purge. No capacity-test timeout is extended.

Unlike the supplied candidate, member rows, channel and state remain intact until the ticket-bearing delete is processed by the owner. Losing/expiring a keeper before dispatch rebuilds the same ticket from the still-frozen DB audience; a count/version mismatch fails. The owner acknowledgement is verified by lifecycle-ticket consumption, not by enqueue success. The API then stores `delete_dispatched=true` guarded by version and ticket. Partial cleanup retries use that flag without preparing a new audience. Channel and state are removed together in the final logged/transactional batch, after secondary cleanup. Guild purge now also deletes ordinary channel main rows and channel indexes.

Delivery is at-least-once at the owner-processing boundary, **not exactly-once or device/WebSocket receipt acknowledgement**. A crash after owner processing and before the durable flag may repeat the idempotent delete event. No background recovery scanner or new global outbox is introduced: a failed request must be retried. Existing relay/session delivery guarantees are unchanged. Old partial-purge candidates are not automatically repaired.

Unarchive emits a bounded reload request. Ticket-specific timeout messages prevent a silent worker failure from leaving a queue stuck forever; overflow/failure falls back to the existing complete reload. This is state recovery, not a guarantee that every WebSocket event is replayed once.

## Validation and rollback

See the integration package validation report for commands actually run against the integrated source. Historical WSL reports establish prior-candidate behavior only. No live Cassandra/Postgres migration, normal-API 100,000-member destructive scenario, multi-node restart test or capacity workload is implied by offline tests.

Rollback first pauses affected acceptance and drains mention consumers again. Do not resume old consumers on v2 records, downgrade the decision/dispatch version, remove the allowlist, or relabel old leases as v2. Preserve v2 readers/consumers until queued work is handled conservatively. Rollback first stops new behavior and new joins above the former cap, while retaining readers, bounded loaders, ticket/decision columns and cleanup/leave support for existing large threads. Never truncate memberships or drop tickets/decisions to fit old code. Do not restore plain-message device push. A binary rollback to an old partial-purge implementation is unsafe for pending new deletions; finish or explicitly recover them first.
